# Tools the app gives agents

The app gives every agent it starts a set of tools of its own, alongside the runtime's
tools, on every runtime (see [Runtimes](runtimes.md)). This page lists them all, in the
order an agent sees them. Every runtime takes them over a local http address the app
serves on this computer only, with a key only that agent's session holds; the key stops
working when the session ends. Copilot uses its own follow-up suggestions instead of the
app's.

The last column says whether you are asked before the tool runs. Where it says the app
answers, the runtime's permission question is answered by the app and you do not see it.
Where it says the runtime decides, you get the same permission card as for any other tool
if the runtime asks; Claude and Cursor ask, and Copilot asks before every tool call.

There's no tool for ending a turn. The app works out how each one ended: **Complete**, or **Waiting on your answer** when a question card is open or the agent's last words ask one, with the first sentence of its last message under its name (the question, when it waits on one). A turn that stopped short (cancelled, refused, out of tokens, failed) shows how it stopped instead. The conversation's name comes from the runtime, or from your first prompt when the runtime sends none. When a runtime advertises ACP's session system-prompt capability, the app sends the briefing as an appended system prompt on session creation and when it loads, resumes or forks a session. Otherwise it uses a runtime compatibility adapter where available, or puts the briefing before your words in the first prompt. This keeps the title based on your prompt whenever a separate channel is available. Every agent's briefing names the three ways a turn ends (#1801): an agent that cannot carry on without you asks, with its own question tool or `ask_question`, and ends its last message with a question only when it asks you one (#1916); one that is done and has something for you (a report, a document, a diagram) calls `show_file` on it once and ends the turn, without archiving; one that is done with nothing for you cleans up and calls `archive_session` with no id. The briefing also says who is who (the runtime's name, your name and pronouns from **Settings**, and who started a helper), what to ask you and what to decide and tell, to show a report you asked for before writing it, to use workflows, helpers and `read_session`, and, where they apply, `move_worktree`, the runtime's tools that do not work in the app and the persona's prompt (#1806). It ends with a line for each of the app's other tools that this host lists, with when to use it (#3608): `notify`, `set_session_labels`, `docs_search` and `docs_read`, `estimate_issue`, and the machine tools with `bring_back` and `move_session`; the browser tools, `fill_secret`, `generate_secret`, `capture_secret`, `pair_web_page` and `hand_to_person` (not on a bot's machine) where the browser is offered, saying they take the browser lease themselves; and `drive_screen` where desktop control is on. Claude defers MCP tools and reads a tool's description only when it looks for that tool, and a folder's `AGENTS.md` and skills reach only that folder, so a test fails when a tool is named nowhere in the briefing without a reason. After you edit a live page, the agent's next prompt quotes the passages you changed. `finish_turn` was removed; a conversation that began before then can still call it, and what it says is kept.

| `show_file` | Opens a file in the files pane beside the conversation, at a line. A Markdown file opens as a page that follows the agent's edits; an HTML file opens rendered, with scripts and the network off (see [Look at an HTML page](../how-to/look-at-an-html-page.md)). | `manage_workflows` | Lists, reads, writes and removes this project's workflows (they live in `.agents/workflows`, which every folder of the project shares through Git, and `hosts:` picks the machines that run each; #3277), turns them off and on, and runs them. `run` is **Run now**, with three more limits: an agent cannot run a workflow that is turned off, that waits for your OK, or that runs in its triggering agent, and a run started by a workflow's agent counts towards the chain limit of three, so workflows cannot run each other in a loop. A workflow an agent writes or changes appears on the folder page straight away, waiting for your OK: it does not run until you click **Approve**, and you can archive it instead. A new one an agent writes also starts turned off, and its page says **Off: written by an agent** until you turn it on. An agent can turn any workflow off, and turn back on one an agent turned off. One you turned off, one an agent wrote, and one whose file says `enabled: false` for any other reason (such as a ready-made workflow) are yours to turn on: `enable` asks you with a Needs you card (**Approve** or **Deny**, #4538), and the app turns it on only when you approve it, as your own switch does. On a machine only agents use, where nobody answers, it is refused. Off and archived are lines in the workflow's own file (`enabled: false`, `archived: true`), so turning one off writes that file; an agent's rewrite of a workflow keeps whatever those lines said. There is no limit on workflows waiting for your OK. Up to 20 approved workflows may be on in each folder by default; the person can set the limit from 1 to 100 in Settings ▸ Cost. Turning one on past the limit is refused until you turn one off or archive one in that folder. See [Workflow triggers and actions](workflows.md) and its [limits](workflows.md#limits). | No. The app answers. |
| `manage_connectors` | Lists this folder's connectors, the MCP servers in its `.agents/mcp.json`, and whether each waits for your approval (#4538). `approve` asks you to approve one that waits, with a Needs you card on the Mac, the Remote and the web page that names the server, the folder and the session (**Approve** or **Deny**). The app approves it only when you approve it, and only as the entry was when the agent asked: an entry changed since is not approved. The agent role still cannot call `mcp/approve` itself. | Your answer on the card. |
| `ask_question` | Asks you a question or a short form and waits for your answer. Named `ask_form` until #2298; Antigravity's own question tool has the same name, and the brief tells the two apart by whose they are. Reaches you on the Mac or on your phone. Used when the runtime has no working ask tool of its own, or when that tool never reaches the model. | No. The app answers. |
| `ask_secret` | Asks you for one secret, such as an API key, by its name (`OPENAI_API_KEY`), with why the agent needs it and, when it knows, a link to where you get it (#2885). Every client shows a card with a masked field. **Save securely** seals what you type in your `~/.agents-secrets/sealed.json` on the machine that runs the agent, the store **Settings ▸ Secrets** and connectors' `${NAME}` use, which only agentsd opens; a secret saved there already is replaced, and the card says so. The agent is told the name and to read it with `agents-secret NAME` (below), never the value. The chat shows *OPENAI_API_KEY: Saved to your secrets*, and the value is not in the chat, the agent's record, the logs or a notification: a notification of it has no **Reply**, and voice mode says it needs your screen. Waits as `ask_question` does. **No thanks** tells the agent you did not give it. A secret saved with **Ask before use** (#4014) is sealed with a flag that makes each use ask: the agent is told that `agents-secret` refuses it, that it is not in its environment, and that it uses it with `fill_secret`, `set_ci_secret`, or as `${NAME}` in the `url` or a header of an **http** server in `.agents/mcp.json` (#4120). Such a server is given to the runtime as a route of agentsd's own (`http://127.0.0.1:<port>/mcp/secret/<route>`, with the session's token); agentsd adds the value on each request it sends the server, so the value is never in the runtime's config or process. The route's first request asks a person, as a Needs you request of kind `approve` for the use `mcp` and the server's name (**Always Approve** is a grant for that server, for every session), and is never held: a start never waits on a person. Until they allow it, each request gets an error that names the request to wait on; once they do, the session's runtime starts again at its next turn and connects. A deny holds until the runtime starts again. A **stdio** or **sse** server with such a `${NAME}` is left out, as one missing a secret is. agentsd's own uses do not ask: a marketplace's registry token or the Atlassian app's client id and secret with Ask before use is not used, and the marketplace list says so. With `secret_description` (#4167) the agent says what the secret is for (which account, which scopes, whose); the card shows it under the name in a **Description** field the person can change before **Save securely**, and the secret keeps it. A description that looks like a value is refused. | No. The app answers. |
| `agents-secret NAME` | A command on every session's `PATH`, not a tool (#4178): it prints the value of one of your secrets with **Ask before use** off, for the agent's own command (`NAME="$(agents-secret NAME)" your-command`), with no newline after it. It is `agentsd secret`, as git's and gh's credential helper is `agentsd credential` (#3926): the session's environment holds a grant (`AGENTS_SECRET_URL`, `AGENTS_SECRET_GRANT`) that can ask agentsd for a value and nothing else, made when the runtime starts and taken back when it ends. agentsd reads the session's own secret first, then this machine's store, and records each read as `secret.read` with the use `command`, the place `agents-secret`, the session and the name. A secret with **Ask before use** is refused, from a session too, with words that say to use `fill_secret`, `set_ci_secret` or an **http** server's `${NAME}`, or to turn the flag off: a flagged value never goes into a process. A call with no grant, such as from your own terminal (#4179), asks you: it calls `secrets/terminalValue` on `daemon.sock`, which any process of your account may call, and agentsd opens a Needs you request (`secretUse`, use `terminal`, the place the name of the command that ran it, as that command says it), with **Approve**, **Approve for 1 Hour** and **Deny**. The command waits, says once that it waits, and prints the value when you allow it. Approve for 1 Hour lets every call of `agents-secret NAME` with no grant through for an hour, and is kept in agentsd's memory only, so a restart asks again. A read is recorded with no session and the place `terminal`. The row says the known gap: Agents cannot tell a terminal from an agent outside its session, so an hour's allow is open to every caller with no grant for that hour. From a terminal, run `agentsd secret NAME` from `Agents.app/Contents/Helpers` (`AGENTS_ROOT` names another root). The brief names it. | No. agentsd answers. |
| `list_secrets` | Lists the person's secrets and the calling session's own (#4167), a JSON line each: the name, the description (*No description* when it has none), the kind (`card` or none), whether it asks before use, whether this machine has a copy (`onThisMachine`; a secret of the person's that waits for one of their apps to seal it here says false) and `sessionOnly`. Never a value, and never the last 4. It reads this machine's files and the control plane's last message, so it never waits on a person. Its words say to call it before `ask_secret`, so an agent does not ask for a secret the person has given already. | No. The app answers. |
| `start_session` | Starts another session in this folder with a prompt of its own, marked as started by this session. It can choose the runtime, model, a permission mode no looser than its own, and whether to work in the folder, a new worktree, an existing worktree or a branch. If the project would go over either of its two helper limits, how many may be running and how many may exist not yet archived (3 and 5 unless you set them in **Policy**), counted across all the project's folders on every machine (#3281; a lead does not count, and a machine that cannot reach the control plane counts its own folders and says so), the session is **queued** instead, and the answer says which limit, names the sessions holding it and gives its place in the queue. A queued session runs nothing until a running place and a not-archived place are both free, behind working and waiting agents, and then starts by itself, oldest first; it shows under **Waiting** as **Queued, 1st**, **Queued, 2nd** and so on, and survives a restart. Past the third limit, how many may be queued (5 unless you set it), the start is refused, naming the limits and sessions. A runtime that can't take an agent on this Mac (not installed, not signed in, or out of the pool on the **Agent Runtimes** page) is refused before anything starts, with the reason and the runtimes that can; so is a model the runtime doesn't offer, naming the ones it does. With no runtime named, it starts on Claude, which is checked the same way. With `machine`, it starts the session on another of your machines instead, by its name as `list_machines` shows it, in this project's folder there, or with `folder` in that folder (an absolute path on that machine), such as a folder of another project. With `machine` alone, a project with no folder there, or more than one, is refused, naming them; so is a folder in no project (#3277). Agents asks you first, on the agent's question card, and nothing starts without your yes, unless you turned on **Agents may start sessions on my other machines without asking** in **Folder Settings ▸ General** (#2928). With `send`, the branch the agent is on, with its uncommitted changes, goes to that folder first, as **Send to ‹server›…** does; a folder there with work of its own, or a machine that is not running, refuses before you are asked (#2929). A stopped machine is started, and the session starts when it connects. That session's chat says which agent started it, and on which machine. This project's limits count it, and a start past them is refused, not queued. `list_sessions` with `started_by: me`, `stop_session` and `archive_session` reach it by its id through the control plane, and only for the agent that started it; its end comes back to a wait on `agent.ended` (#2887, #2927). `read_session`, `message_session` and a wait on `agent.ended` reach it as any session of the project (#3277). | The runtime decides. |
| `stop_session` | Stops a session this agent started, or one below it, as your **Stop** would. That frees its running place; it keeps its not-archived place until it is archived. A queued one is taken off the queue and never starts; so is one you or the agent archives. | The runtime decides. |
| `archive_session` | With no id, archives the agent's own session once its turn ends. Its description tells the agent to call it when its work is done and nothing is left for you to see, and not when it showed you a file, asked you a question or has a report for you. It archives if the turn ends **Complete**, **Nothing to do** or **Partly done**; an ending that asks you something else (a question, stuck, waiting on others) drops it, and so does anything you send first. Where it needs your approval, the session then carries an **Archiving needs approval** mark and is listed in **Needs You**, with a card at the end of its chat, until you click **Approve** (see [Statuses and groups](statuses.md#archiving-needs-approval)). A workflow's run its workflow lets archive itself (`when-done: archive-allowed` or `archive`, see [When a run is done](workflows.md#when-a-run-is-done)), or a session started by another in a folder where sessions may archive the sessions they started, is archived without your approval, if the turn ends **Complete** or **Nothing to do**. It goes with `move_worktree`: the agent moves, and stays there waiting for approval instead of being started again. With an id, for a session this agent started or one below it, once its work is merged or abandoned: where **Sessions may archive the sessions they started** is on in **Folder Settings ▸ General** (on unless you turn it off), it is archived now, as your **Archive** would, or when its turn ends if it is still working (if that turn ends **Complete** or **Nothing to do**; otherwise it waits for your approval). Its conversation says which agent archived it, `agent.archived` says `by` another agent, and you can unarchive it from **Archived**. Where the switch is off, it waits for you to approve archiving it. Either way its running place is freed once its turn has ended; it keeps its not-archived place until it is archived. Refused, in words, for your own sessions, a workflow's, and sessions not below this agent. | The runtime decides. |
| `move_worktree` | Moves the agent once its turn ends. On Claude, Copilot, Cursor and Codex only: the runtimes that can carry the conversation into another folder. `worktree` names a new worktree of the folder or gives the path of one that exists, and `leave_worktree` (`keep` or `remove`) goes back to the folder. Neither takes back a move it asked for. The agent is started again there to carry on, unless it also asked to be archived. A move doesn't go with a wait or with **Waiting on your answer**. Nothing uncommitted comes along. Removing takes the branch too when the app made it and it is merged; an unmerged branch is kept with its commits, so a lane can remove its worktree as soon as its work is committed. Removing is refused for a worktree the app did not make, another agent works in, or that is detached or whose branch is gone (its commits would be on no branch), and, unless the agent says to discard, when anything in it is uncommitted. The refusal names the files. | The runtime decides. |
| `set_session_labels` | Adds or removes labels the agent owns on its own session, at once. It cannot remove or claim one of yours. A label `#n` or `P#n` (or a Linear key, such as `ENG-4`) also links the session to that issue or pull request in the lineage graph; taking the label off ends the link (#2349). | The runtime decides. |
| `list_sessions` | Lists the sessions in this project, most recent first, its own included: each one's id, title, runtime, status, worktree and branch, the resources it holds, and what it last said. That is every folder of the project on this Mac and, through the control plane, on your other machines (`projects/sessions`); a session in another folder says which, and one on another machine says which machine and folder. A machine that did not answer is named at the end. A folder in no project, or a Mac on no control plane, lists only what is here (#3277). If this agent has a message waiting for a session, that line says so with the text. Nothing from another project. With `started_by: me`, it lists only the sessions this agent started, and the ones below them, that are not archived (one it did not start itself says who did), what each is doing and last said, after how many of the folder's running and not-archived places are in use, such as "2 of 3 running, 4 of 5 not archived", with ", 2 of 5 queued" once any are. A queued one says `queued (position 1)`. It ends with the runtimes `start_session` can start one on here, as of that moment, each with its model where this folder has used it, and why each of the others can't. | No. The app answers. |
| `read_session` | Reads one session in this project, on this Mac or another of your machines, by its id or exact title: what you asked, what the agent said, the tools it ran and the files they touched, what it said of how the work went, and its plan as it last stood. If this agent has a message waiting for that session, the header includes it. A long one keeps the first request and the latest turns and says how many were left out. Reading it changes nothing. A title used twice, a deleted session, or one not in this project is refused in words. Used when you ask an agent to continue another session's work. | No. The app answers. |
| `message_session` | Sends words to another session in this project, on this Mac or another of your machines, by its id or exact title. It reads them as a prompt marked as the sender's, and its chat shows them as "From" that agent on the Mac, the Remote and the web. A session that is working reads it after its turn; one that is done is woken by it, yours included, within the folder's running limit for sessions started by sessions; one that is stopped, or one waiting on your answer, is not woken: the message waits in its chat for you. It never answers a question or permission card. A session that another session started takes messages only from that session; a message to it from any other session is refused, and nothing is sent (#1695). A message to a session in a looser mode, or with its sandbox off while the sender's is on, waits in its chat for you, unless that session started the sender or ran the sender's workflow: then it goes at once (#1728). One queued message per sender and target: a second send while the first is still waiting is refused, quoting the waiting text; `replace: true` swaps that text and keeps its place. `cancel_message` takes it back. A message held for a looser target still counts as the one queued. Limits: 4,000 characters and 30 new messages an hour per sender; replace and cancel do not count towards the hour. Raises `agent.messaged` on a new send, not on replace or cancel. | No. The app answers. |
| `cancel_message` | Takes back this agent's queued message to another session of this project on this Mac, by its id or exact title. It says when nothing is waiting (already read, or nothing was sent). Only this sender's own message is removed; the person's queued prompts are left. | No. The app answers. |
| `lease_resource` | Takes a turn with something only one agent should use at a time: a simulator, a browser, the screen, or anything it names. If someone else holds it, it answers at once with the agent's place in line, which is a wait for its `lease.granted` event (#2361). `capacity` (#4579) is on every machine, and is granted only while the machine's level is ok; it and `build` go in line while the machine is near or full, also with a free place, and the reply says why. A lease lasts 30 minutes unless the agent asks for up to 240 (or the declared resource's own lengths), and calling it again extends it. A declared resource may allow more than one holder at once. | The runtime decides. |
| `drive_screen` | Drives a named app on this Mac through its own screen, mouse and keyboard, for a task no API reaches: a non-browser app, or an app's own GUI. Takes the `screen` lease the first time it is called, the same way `lease_resource` would; a second agent calling it queues behind the first. `click` presses by label (the element's title, description, value or help) or by `x,y`; `type` sends real keystrokes; `key` presses one named key; `read` answers with the app's own accessibility tree; `screenshot` answers with a picture of the whole screen, sent once and not kept. Needs a Mac with `agents-drive` beside this host, **Desktop control** turned on in Settings ▸ Machines ▸ This Mac (off by default), and Accessibility granted to it; refused, naming the rule, otherwise. When the person moves the real mouse or presses a real key while the agent holds the lease, the call stops where it is (typing stops part way) and waits: every client shows a card with **Resume**, which goes on from where it stopped, and **Take Over**, which lets go of the lease at once and refuses `drive_screen` for the rest of that turn. While it holds the lease, every client showing the session draws a live tile at the chat's end: the latest picture of the whole screen (*Mac is locked* and no picture while the screen is locked) and the last action in words, after each action and at least every 5 seconds (`desktopControl/liveFrame`); no picture is kept. | The runtime decides. |
| `browser_navigate`, `browser_snapshot`, `browser_click` and the other `browser_*` tools | Drive this machine's browser (#3534): the tools of the Playwright MCP server (`@playwright/mcp`, the version this host carries), under their own names. The first call installs Node, and Chromium when there is no Google Chrome (below), on this machine when they are not there yet, starts the browser, and takes the `browser:agents` lease, the same way `lease_resource` would; a second agent queues behind the first and is told its place. The host starts one Playwright server for the session, in its folder, and passes each call through. Every result goes through the host first: the value of each secret filled into the page comes out as `<secret NAME>`, and a link to a file Playwright wrote (the page after an action, new console lines) names the tool that reads it instead, such as `browser_snapshot`. The lease and the Playwright server end with the agent's turn; the browser, its pages and its sign-ins stay. The browser has no passkeys (#4084): Chromium starts with WebAuthn off (`--disable-blink-features=WebAuth`), so a page sees no `PublicKeyCredential` and does not wait on a passkey dialog nobody sees; agents sign in with a password and TOTP (#3908), and `browser_passkey` starts it again with WebAuthn for a site that takes only a passkey (#4085). On a Mac with Google Chrome installed (`/Applications` or `~/Applications`), the browser is that Google Chrome stable, for every site (#5207): in a profile of its own (`browser/chrome-profile`, beside Chrome for Testing's), with a window moved just below the screen as it starts, and with none of the test flags (only the profile, the debugging address and a free port agentsd picks (port 0 makes Chrome set `navigator.webdriver`), the cache size, `--no-first-run`, `--no-default-browser-check` and the window size; no user agent set). It downloads no Chromium; it has a Dock icon of its own while it runs. Elsewhere (no Chrome, a Chrome that does not start, and Linux until #5209), it is Chrome for Testing, which Playwright installs: headless, except that `browser_navigate` to a site whose bot check refuses headless Chrome (Cloudflare, Microsoft's sign-in and sign-up, Paddle's checkout; `Go/internal/browser/checks.go`) starts it again with a window, far off-screen, until it stops (#4272): the pages open again at the same sign-ins, and the agent's next call reaches the new browser. Neither hides that it is driven: no fingerprint is changed and the user agent is the browser's own (#4272, #5127). Not listed on a machine where the browser cannot be installed. | The runtime decides. |
| `fill_secret` | Types one of the person's secrets (Settings ▸ Secrets) into a field on this machine's browser's page (#3530), named as `browser_type` names it (`target`: a reference from `browser_snapshot`, or a selector), and presses Enter after it with `submit`. A card secret (#3531, Settings ▸ Secrets ▸ Add a Card…, only a card with a spend limit) is filled a part at a time with `part`: `number`, `expiry` (MM/YY), `exp_month`, `exp_year` (YYYY), `cvc`, `name` or `zip`; the agent gets `<NAME> <part> filled.`, and from then on every part of the card is out of what it reads, the number as `<secret NAME.number ending 4242>` and the CVC wherever it stands as a whole number. The host opens the value from its sealed store and types it through the agent's Playwright server; the agent gets `<NAME> filled.`, never the value, and the record keeps the name and the field only. After the fill the field is drawn as dots (`-webkit-text-security`, drawn so again when the page changes its style), so screenshots and the stream show no value; every browser result has it out as `<secret NAME>`; `browser_evaluate` is refused on a page with a filled field until the page navigates; and while any value is filled into the browser, `browser_run_code_unsafe` and any call with `filename` (a file would skip the filter) are refused. A field that cannot be drawn as dots is emptied again. A secret that is not set yet is refused with words that say to ask for it with `ask_secret` first; one shorter than four characters is refused, as the filter cannot hide it. A secret with **Ask before use** (#4014) waits on a person's approval for the field's domain (#4015): a Needs you request of kind `approve`, answered **Approve**, **Approve for This Session**, **Always Approve** (a grant for that domain, for every session, kept sealed with the secret) or **Deny**, by the person's own clients only. The call is held as `ask_question`'s is; after the hold, it names the request, and the agent waits for it with `wait_for_event` `where: {request: <id>}` and calls again. A deny is an error that says a person denied it. The promise is `ask_secret`'s: an agent that tries hard can read a secret with Ask before use off with `agents-secret NAME` or reach Chromium itself; the sandbox is the wall. Listed with the browser tools. | The runtime decides. |
| `generate_secret` | Makes a strong password with `crypto/rand`, saves it in Settings ▸ Secrets as `secret`, and types it into a field on this machine's browser's page as `fill_secret` does (#4000); the agent gets `<NAME> made and filled.`, never the value, and the page is closed to it as after `fill_secret`. `rules` takes the site's rules in the [`passwordrules`](https://github.com/whatwg/html/issues/3518) format (`minlength`, `maxlength`, `required`, `allowed`, `max-consecutive`) or a preset, `alphanumeric` or `pin` (with `length`, default 6). With no `rules` it reads the field's own `passwordrules`, `minlength`, `maxlength` and `pattern`; when the field has none, 24 characters of lower, upper, digits and symbols. It uses the longest length the rules allow (at most 128), one character of each required class, and refuses rules no password meets, with the reason. A name that exists is refused unless `replace` is true, which keeps the old value as `<NAME>_PREVIOUS`. A confirm field is filled with `fill_secret` and the same name. Listed with the browser tools. | The runtime decides. |
| `capture_secret` | Saves a value that this machine's browser's page shows once (an app password, an API token) in Settings ▸ Secrets as `secret` (#4028). `target` names the element as `browser_click` does; the host reads its text, or a field's value, and saves the first match of `pattern` (a Go regular expression), or the whole text trimmed. The agent gets `<NAME> saved (N characters).`, never the value, and from then on every browser result has it out as `<secret NAME>`. It refuses, without saying what it read, when nothing matches or the match is shorter than four characters. `set_session_labels` adds or removes labels owned by the agent. `start_session` can give
the new session up to five labels, which it owns from its first moment. Labels are
unique within a session without regard to case. An agent cannot remove or claim a
person-owned label; the whole call is refused if it tries. See
[Label a session](../how-to/label-a-session.md).

`start_session`, `stop_session`, `archive_session` and `list_sessions` with `started_by: me`
are given to every agent, including one another agent started (#940). The folder's helper
limits are the bound: they count every session an agent started, whoever started it. An agent
can stop, archive and list the sessions it started and every session below them (the
sessions those started, and so on), never your sessions, a workflow's, or another agent's.
Each session keeps its direct starter, so the chain shows who started whom. Archiving or
stopping an agent leaves the sessions it started working; every agent above it, and you, can
still stop or archive them. Every agent is told, once at the start, to ask to
archive its own session in its last turn, once its work is merged or abandoned and cleaned up (#703).

Before #638 these were `start_agent`, `stop_agent`, `request_archive`, `archive_agent`,
`list_my_agents` and `message_agent` (and `park_agent` before `request_archive`). They are
no longer offered or answered; a conversation that called them still shows those calls as
the app's own.

A session started by another counts as **running** while it is working, waiting on a question or permission,
starting, or waiting to carry on by itself: waiting on other agents, a time or
events, or waiting for an allowance. Finished, stopped and archived helpers don't, nor does
one waiting for archive approval. So a lead that stops a helper whose part is done, or archives
it, frees a running place once its turn has ended; the
helper's not-archived place stays taken until it is archived. A lead should archive a
helper once its work is merged or abandoned, rather than remove the helper's worktree under
it; archiving removes a worktree the app made for it once everything in it is committed. Both limits are yours alone to
change: the tools only read them. They are kept in the folder's `.agents/folder.json`;
a value written there by hand is held to the maximums. `list_sessions`, `read_session`, `message_session` and `cancel_message` are
given to every agent, including one another agent started.

**The project is the unit (#3277).** These tools reach every session of the agent's
project, not only its folder's: the other folders of the project on this Mac, and, through
the control plane, the project's folders on your other machines. The control plane asks
only your own machines, and only for a machine with a folder of the project. Permissions do
not change: an agent still stops and archives only the sessions it started, and a session
another session started still takes messages only from that session. A lead (#3265) uses
them to see, read and wait on the lanes of its epic on every machine of its project.

The five machine tools are given to every agent. The control plane does what they ask as
it would for you, and its log names the agent that asked. Agents reach providers only
through the control plane, never directly.
