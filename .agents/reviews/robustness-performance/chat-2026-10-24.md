# Chat responsiveness review — 2026-10-24

Reviewed issue #1316 on `main` at `31289a2d`. Issue #1315 was closed before this review.

## Method

- Read the chat path in the Mac and Remote shared UI, the web client, the AgentsKit turn model, and the Go transcript service.
- Used `scripts/seed-archived.swift` to create synthetic chats on scratch roots. No live agent records were read or copied.
- Ran a Debug Agents Host and Mac window on an M5 Mac. The large chat held 482 synthetic agent messages and about 1 MB of transcript data.
- Used `sample` for the Mac window, Chrome DevTools performance metrics for the web page, and nine JSON-RPC calls per daemon measurement.
- Closed each scratch root and the headless Chrome profile after use.

The initial window launch failed because the scratch processes ended with the command. I then kept the scratch launcher alive and completed the Mac and daemon measurements. I did not capture a profile while the Mac drew or scrolled the chat. The Mac sample below is an idle sample after the chat loaded. The prompt measurement uses the walk socket, so it is not a direct measurement of typing latency.

## Summary

One medium finding: a turn with many short messages stays in one large row. The shared Mac and Remote UI cuts one long Markdown message into rows. It does not limit the number of messages in one row. The web client also draws the turn as one article.

The 1 MB sample had 482 messages. The web page showed one turn with 393,029 characters in a 78,199 px scroll area. It took 102 ms from selecting the chat to two animation frames. Chrome recorded 57.7 ms of tasks, including 17.0 ms of script and 30.4 ms of layout. The Mac accessibility tree reported a 60,459 point tall text element.

Finding: [#2572](https://github.com/alexec/Agents/issues/2572).

## Finding

### C1 — Medium: a turn with many short messages stays in one row

**Where:**

- `Packages/AgentsKit/Sources/AgentsKitCore/UI/TurnRows.swift:33-61` splits a long individual message by Markdown block count. It does not cap the number of outcome items in a row.
- `Shared/UI/Chat/ChatTranscript.swift:224-239` creates rows for each turn and passes those rows to the transcript stack. Mac and Remote share this view.
- `Shared/UI/Chat/TranscriptRows.swift:120-125` collects step items for a turn.
- `Web/src/views/Chat.tsx:586-592` draws one `TurnView` per turn.
- `Web/src/views/chat/Rows.tsx:593-619` folds and maps all items in the turn into that article.

**Measurement:**

| Client or service | Synthetic input | Result |
|---|---|---|
| Mac window | 482 messages, about 1 MB | One large text element measured 60,459 points tall. `sample` after load found the main thread waiting for events in all 2,736 samples. This shows no sustained work after load; it does not measure draw or scroll time. |
| Web in headless Chrome | Same transcript | One turn, 393,029 rendered characters, 78,199 px scroll height. Selection to two animation frames: 102 ms. Chrome: 57.7 ms task time, 17.0 ms script time, 30.4 ms layout time. One run. |
| Daemon, 20 KB chat | 10 entries | Transcript page: 20,679 bytes; 23.0 ms median for 100 entries, 23.3 ms for 500. |
| Daemon, 1 MB chat | 482 entries | 100 entry page: 206,642 bytes and 22.9 ms median. 500 entry page: 995,742 bytes and 41.9 ms median. Nine runs per measurement. |
| Mac prompt field | 47 characters | Walk socket set took 0.13 s wall time. This includes the tool call and is not a typing latency result. |

**Fix:** Limit a row by outcome item count as well as Markdown block count. Keep the rule the same on Mac, Remote and web. The issue proposes 24 outcome items, to match the current 24 block limit. Measure draw and frame time before and after the fix on this same chat shape. The current review has no after measurement because it made no code change.

The Mac and Remote currently draw the chat through the shared `ChatTranscript` and `TurnRows` code. The web has a separate `TurnView` and should use the same row bound.

## Other paths reviewed

- The Go daemon caps transcript pages at 500 entries and turn pages at 200 summaries. The measured 1 MB transcript page took 41.9 ms median. The test transcript had no user prompts, so the turns call returned zero closed turns.
- The Mac and Remote cache folded turns and row cuts. The web memoizes each turn view. These guards reduce repeated work for unchanged turns, but they do not bound the number of outcome items in one turn row.
- I found no other chat performance issue that I could confirm with the available measurements.

## Limits

- The chat was synthetic and contained short agent messages. It did not contain Markdown, tool calls, code blocks, images, or active streaming.
- The Mac sample was taken after the chat loaded, while idle. It did not measure the first draw or scrolling.
- The browser result is one draw measurement. I did not collect a scroll frame-time distribution.
- I made no code changes. No tests were run.
