# AGENTS.md

## Context routing

- **For the project's purpose and setup:** READ `README.md`.
- **For architecture, terminology and decisions:** CONSULT `docs/`.
- **For hosting, sign-in, trust and customer data:** FOLLOW the principles in `docs/explanation/direction.md` (#3403). A spec, plan or issue agrees with them, or says which one it leaves out and why.
- **For a task a skill covers:** USE the skill in `.agents/skills/`.
- **When a task calls for a specialist perspective:** ADOPT a persona from `.agents/personas/`.

## Libraries before our own code

- Before writing a parser, protocol, client, format or algorithm, look for a library. Use it when one fits.
- A fit library has a permissive licence (MIT, Apache-2.0, BSD or ISC; no GPL/AGPL in the apps), was released or updated in the last 12 months, has users, and has a pinned version that Dependabot watches (`Package.resolved`, `go.sum` or an exact `package.json` version).
- Prefer the platform library (Foundation, Go standard library or the browser), then the protocol or service's official SDK, then a widely used community library.
- Write our own code only when no fit library exists or the library costs too much where it runs. State the reason in the PR. For a library added by a PR, state its purpose, licence and size.

## Durable data

- Store data in the project itself when possible.
- When important long-term data cannot safely live in the project, store it on disk in `~/.agents` when safe. Do not rely on an agent's memory for data that can safely be stored there.

## Keeping the three clients in step

- **Three clients draw the same product:** the Mac window (`App/`), the Remote on iPhone and iPad (`Remote/`), and the web page (`Web/`). `Shared/UI` is drawn by both the window and the Remote.
- **Each feature has a tier (#2796):** the Tier cell of its row in the parity table, below. The Mac window and the web page are full clients and are never trimmed; the tiers trim only the Remote.
  - **Core:** all three clients (the session list, chat, question cards, the prompt bar, approvals, notices, the Brief, and the session and folder work the Remote keeps). The parity table lists it all.
  - **Mac + web:** the Mac window and the web page. The Remote gets no parity issue and does not have the feature: #2798 removes it, with no line in its place (Alex, 2026-10-29).
  - **One client:** by design, no follow-up.
  - A new feature that is on neither of the parity table's lists is Mac + web.
- **A change to any client's UI** (`App/Sources`, `Remote/Sources`, `Shared/UI` or `Web/src`) says, in its commit, what **each of the other two** does about it, one line each:
  - the same change in this branch: `remote: same`;
  - a parity issue filed: `web: #NNN`;
  - left out on purpose: `mac: by design (no swipe on Mac)`;
  - not on the Remote because of its tier: `remote: tier mac+web`.
- **For example,** a Mac sidebar change ends with `remote: #226` and `web: same`; a new Settings ▸ People control ends with `remote: tier mac+web` and `web: same`; a web-only fix ends with `mac: same, remote: same` when both already do it. A change to docs only says `mac: docs only, remote: docs only, web: docs only`.
- **The table of where each client stands** is `specs/071-web-remote/walks/parity.md`, a file per screen under `walks/parity/` (Mac / Remote / web, a row per feature; #2020). `scripts/parity-counts.py` counts the verdicts and the tiers. A parity line that changes a row updates it in the same branch.

## Web/dist and generated.ts

- **`Web/dist` is not checked in** (#473); it is in `.gitignore`. Agents Host's build makes it with `scripts/web.sh dist` (the Node in `Web/.node-version`; without it, an empty one and a warning). Run `scripts/web.sh build`, under the "build" lease, to see a web change without a Mac build.
- **The wire's types come from `Packages/Wire` (#1135).** A change to a protocol type changes `Packages/Wire/daemon.schema.json` (or a method in its `*.openrpc.json`) first, runs `scripts/wire.sh gen`, and commits what it makes (`Web/src/protocol/generated.ts`, `Go/wire/*_gen.go`); `WireSchemaTests` then says what to change in Swift by hand. A conflict in a generated file is settled by running that again, never by hand.

- **The design tokens come from `design/tokens.json` (#4602).** A change to a colour, radius, font or type step changes the JSON first, runs `scripts/design.sh gen`, and commits the CSS it makes (`Web/src/theme/tokens.css`, `www/tokens.css`, `docs/stylesheets/tokens.css`, `Go/internal/forgepages/tokens.css`, `Go/internal/paperpage/tokens.css`, `deploy/site/www/oauth/tokens.css`); `DesignTokensTests` then says what to change in `Paper.swift`, `StateTint.swift`, `TypeScale.swift` or the AccentColor assets by hand, and `scripts/lint.sh` fails on a stale file. It also fails on a colour named outside a token file in `Web/src`, `www`, `docs/stylesheets` and the Go pages (#4609): use a `var(--…)` token, or add the colour to `design/colour-allowlist.txt` with why.

## Verifying a lane's work

- **A lane verifies only what it touched:** the schemes and tests for the paths its branch changes, as `merge-wave.sh plan` lists them. An `App/` change builds `AgentsHost` (Agents, the one Mac app); a `Remote/` change builds the Remote; a package change runs that package's tests, filtered by `scripts/select-test-suites.sh`. The full AgentsKit suite and every scheme run once, in the merge wave, which also skips any check that already passed at the same tree.
- **Before a push that changes `Go/`, run `scripts/go-changed.sh`** under the "build" lease (#2994): `go vet` and `go test -race` on only the Go packages the branch changes (all of them for `go.mod`, `go.sum` or `Packages/Wire`). CI's runners are shared, so a Go failure found here saves a run, a macOS one too. It runs the Mac's own Go, not a container (#4709): a failure only Linux has still shows only in CI's `go` job.
- **Lint with `scripts/lint.sh`** (#1224): shellcheck, `zsh -n`, our text checks, and golangci-lint's `unused` and `ineffassign` (#2162) fail CI's `lint` job. The other golangci-lint rules, govulncheck, ruff, Biome and SwiftLint only report, and say which findings are in your files (`LINT_BASE=origin/main`). On the Mac each runs on the host, never in a container (#4709): the pinned binaries go to `~/Library/Caches/Agents-build/lint-tools/` the first time, and Go comes from `brew install go`. With no linter named, a Mac runs only the linters for the files the branch changes (#4710), and says which it skipped; `--all` runs every one, as CI does. `scripts/lint.sh --fix` runs the fix modes.
- **Build through `scripts/build-cache.sh`** (`… xcodebuild …`, `… swift test …`): one package and compilation cache in `~/Library/Caches/Agents-build/` for every worktree, so a fresh worktree is not a cold build. Deleting a worktree's own `build/` and `.build` when done is still the rule; the cache stays. Its `swift test` sets `AGENTS_QUARANTINE=1`, so tests marked `.flakyUnderLoad` skip as on CI; `AGENTS_QUARANTINE=0` runs them.
- **Before any xcodebuild, swift build, swift test, scripts/web.sh build or ship.sh, lease the resource "build" with lease_resource (minutes sized to the job, at most 60), and release it with release_resource the moment the command ends.** Never hold it while reading, editing or waiting on the screen.
- **Close every scratch app you ran** (run-app, the walk simulator, headless Chrome) with the run-app skill's "When you are done" steps before you commit or end. A scratch app left running is a bug in the lane.
- **A walk does not hold a place:** a lane that needs one commits, hands the walk on, and ends.

## Work by epic, release from main (#1340, #3465, #3760)

- **Milestones are themes, not versions (Alex, 2026-11-06, #3760).** A milestone is named by its theme only (`Projects`, `Channels`, `Runtime assessments`), and its GitHub due date gives the order; the due date is only for the order, and the milestone's description says so, with its goal and its place (#1340). `1.0 Public release` is the one milestone that keeps a version. **Why:** since #3465 a version holds more than its milestone, and a new order meant new numbers for every milestone.

- **Work goes by epic (Alex, 2026-11-04, #3465).** The Scrum Master gives places to epics' leads (#3265), several epics at once, under the lane and open-PR limits. When there are more epics than places, the epic in the earliest milestone (by due date) goes first, then core usability (#2800), then RICE. An issue that is in no epic goes by the same order. An issue with no milestone is the backlog, except bugs and enhancements that are no epic's sub-issue, which have standing epics of their own (below): the backlog is the issues with no milestone that neither standing epic takes.
- **A milestone is a set of epics and issues, not a gate (#3465; replaces #2309).** Work from a later milestone can run and merge before an earlier milestone ships. No issue is `parked` for its milestone.
- **A filed issue gets a milestone** only when it serves that milestone's goal (#1340).
- **Bugs have no milestone (Alex, 2026-11-01, #3212).** A bug is filed with no milestone, whatever its theme. The **bug lane** is a standing epic, #4207: its lead works the open bugs with no milestone always, in the background, as ordinary work, `priority:high` first, under the same open-PR limits. The exception is a bug that blocks a milestone's goal; it keeps that milestone, as a competitor gap that serves a goal does. **Why:** a patch milestone held features off `main`, so nobody could test them there, and that slowed the whole cycle.
- **Polish and competitor gaps have no milestone.** Issues labelled `polish` or `competitor` stay out of milestones. The exception is a competitor gap that serves a milestone's goal; it keeps that milestone. They are enhancements, so the standing epic for enhancements with no parent, #4208, works them with every other enhancement that has no milestone and no parent (#4335), alongside the milestone lanes, highest priority first, under the same open-PR limits. They are for no milestone, so they can merge before a release ships (#1570).
- **Standing epics are the standing lanes (#3659, #3664).** A standing epic has the labels `epic` and `standing`, and its plan is a query in a `standing` block in its body, not sub-issues (`specs/3659-standing-epics/spec.md`). It never closes. This folder has two: the bug lane, #4207 (`labels: bug`, `milestone: none`), and enhancements with no parent, #4208 (`labels: enhancement`, `milestone: none`, `parent: none`; #4335). The Scrum Master gives each one's lead a place as it gives a place to any epic; the lead runs the block's `lanes:` lanes at once (1 when it says none) and takes the query's issues in its order: `priority:high`, then `priority:medium`, then no priority, then `priority:low`, the oldest first in each. When places run short, a standing epic's lane is paused before a milestone epic's lane (never a UI lane before a non-UI one). Their blocks are the Product Owner's and Alex's.
- **Spare places go in this order** (#1604, #3212, #3465), always within the open-PR limits: the milestones' epics and the bug lane's epic (#4207) together; then the epic for enhancements with no parent (#4208, #1570, #4335); then backlog issues with no milestone, by RICE.
- **UI changes go early (Alex, 2026-10-22, #2337).** Every choice of what to work on next goes in this order: `priority:high` issues first; then **UI changes**, anything that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`), in the milestones, the bug lane and the backlog alike, bugs before features; then the rest, in the order above (the milestones' epics and the bug lane's epic, then the epic for enhancements with no parent, then the backlog by RICE). A UI lane gets a place before a non-UI lane. When places run short, pause a non-UI lane, never a UI one. **Why:** a person must review each UI change, so it must get to `main` and TestFlight early. A UI enhancement gets its place early too; one that adds a new screen, control or layout merges only after Alex approves it ("A UI enhancement waits for Alex", below, #2811, #3474).
- **Core usability goes first (Alex, 2026-10-27, #2800).** When milestones are put in order, a milestone that improves the app's core usability goes before the others. Core usability is what a person does in the app every day: start a session, choose a runtime, read and answer agents. A milestone that is useful to one person is core usability; a milestone that reaches people who are not the user (Hosted, Channels) is not. **Why:** this is why Auto runtime and voice mode and Lineage and value went before Hosted and Channels. The order is in #1340 and in each milestone's description.
- **No patch milestones (Alex, 2026-11-01, #3212; replaces #2801 and #2779).** A release makes no `x.y.1 Bug fixes` milestone, and nothing is held for a patch: enhancements merge as usual (a UI enhancement still waits for Alex's approval, #2811). **A release ships what is on `main`:** when a bug fix must reach people sooner, the next release takes it. Every release is a minor (x.y.0).
- **The release reviews are paused until 1.0 (Alex, 2026-11-01, #3215).** The release runs no security, performance, HADR, dead-code or usability review: before 1.0 the product changes too fast for them to pay back what they cost. The dead-code review runs on its own schedule instead (Tuesday, Thursday and Saturday; Alex, 2026-11-06, #3715). It still runs the runtime check, the competitor check and the feature matrix, and files a `priority:high` bug for each critical or high Dependabot alert. #3216 brings the reviews back at 1.0, at PR time. The other four reviews' skills and workflows stay, turned off.
- **Releases go out from `main` on their own schedule (#3760; replaces the #3465 gate).** A release starts when something merged since the last tag, at most one a day, and is the next minor. No milestone blocks it, except that the release that takes 1.0.0 waits until `1.0 Public release` has no open item.
- **A milestone never closes with open issues (Alex, 2026-10-22, #2455).** The release skill closes only a milestone whose items are all closed. **Why:** nothing schedules an issue left in a closed milestone.
- **One release a day (Alex, 2026-10-22, #2462).** At most one tag per calendar day in America/Los_Angeles; the release skill's readiness check and gate wait for the next day.
- **A milestone is done when its last item closes** (#3760), not when a release ships. It reaches people in the next release, whose notes name it under `## Milestones finished`; the release skill then closes it.

## Plans: features, epics, stories, tasks and spikes (#3265)

- **Work has one hierarchy** (`specs/3265-work-plans/spec.md`). The level is a label, used in addition to the type label (`bug`, `enhancement`), which the rules above and below still use:

  | Level | On the forge | Worked by |
  |---|---|---|
  | **Feature** | the label `feature:<name>`, a product theme; spans epics and milestones | nobody directly |
  | **Epic** | a parent issue, label `epic`; its children are its plan | one lead |
  | **Story** | a sub-issue, label `story`: a person can see or use it (a client or a workflow changes) | a lane: one PR or one stack |
  | **Task** | a sub-issue, label `task`: it changes no client (daemon, wire, tooling, docs) | a lane: one PR |
  | **Spike** | a sub-issue, label `spike`: a question with a time limit; it ends in a decision in the issue or a spec, not product code | a lane, or the lead |
  | **Bug** | label `bug`, as before; it can also be an epic's child | the bug lane, or the epic's lead |

- **A feature is a label, not an issue,** because a feature outlasts its epics. An epic belongs to one feature, and its children get the same `feature:` label. Only open issues get `epic` and `feature:`; closed epics keep their labels.
- **`feature:<name>`** is the product theme that the Product Owner sets when it files the issue. There are no `area:<name>` labels any more (Alex, 2026-11-10): the areas of #873 locked a set of paths to one lane at a time, and that lock held work up more than it saved rebases.
- **Every issue gets a size when it is filed (Alex, 2026-11-10, #4532).** Every agent that files an issue (the Product Owner, a lead, the bug lane, a review or check) sets one `size:` label, `size:XS` to `size:XL`, from the points rubric in `.agents/personas/product-owner.md`. An epic gets none. Never change a size after filing: the backtest in `specs/3557-estimates/spec.md` compares it with the actual cost.
- **The order is in the forge, not in prose.** The children are the epic's sub-issues, and a child that must wait is "blocked by" the children it waits for. A **step** is the set of children whose blockers are all closed or in an earlier step; the children of one step can run at the same time, under the open-PR limits. A "Slices" table in the epic's body is optional prose: the sub-issues and their "blocked by" links are the plan.
- **One lead per epic** (the `lead` skill, `.agents/skills/lead/`). The Product Owner files the epic and its first children; then the lead owns the plan: it starts a lane for each child whose blockers are closed, files the new children that its lanes find, and closes the epic when all its children are closed. The lead writes no code.
- **The Scrum Master gives a place to the lead, not to each child.** The lead does not count as a lane; its lanes do, towards the folder's lane and open-PR limits (typically 5 to 7 at once, per project). The milestone order and "UI changes go early" apply to the epic as one unit.
- **The app says "epic"** for every forge, also for Linear.

## Landing a change

- **Every change has an issue and a pull request.** Work on a branch of your own, in a worktree you moved into with move_worktree (never one made by hand with `git worktree add`, which the app never sees: #615), push it, open the PR with `gh pr create`, turn on `gh pr merge --auto --squash` at once, and wait for it to land; fix what CI fails. Never push to `main`.
- **A UI enhancement waits for Alex only when it adds a screen, control or layout (Alex, 2026-10-27, #2811; scope 2026-11-04, #3474).** An `enhancement` PR that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`) merges only after Alex approves it **when it adds one of these:**
  - **a new screen:** a window, sheet, pane, page, popover, tab, or a Settings section;
  - **a new control:** a button, menu item, toggle, field, picker, swipe or other gesture, or a keyboard shortcut;
  - **a new layout:** it moves, regroups or removes sections or controls of an existing screen, or changes how a person gets to a screen (navigation).

  **Every other UI enhancement auto-merges at once,** as a bug fix does: copy, colour, spacing, fonts, icons, the state or look of an existing control, empty states, and polish. Its body still has `## Screenshots` (one per state and per client, step 1), so Alex can look later and comment. A bug fix, and an enhancement that changes no client (daemon, wire, tooling, docs), never wait.
  - **The lane decides, and writes one line in the PR body:** `Approval: needed (new control: …)` or `Approval: not needed (no new screen, control or layout)`. When the lane is not sure, it asks for approval: a wrong "not needed" costs Alex one comment and one follow-up PR.
  - **When Alex comments on a merged PR that did not wait,** a lane changes it or reverts it, on a new PR.
  - **Why:** agents' walks find out whether a change works, not whether it is right for a person; 102 of the 296 bugs filed from 2026-10-20 to 10-27 came from the usability check, after the change had merged. But from 2026-10-28 to 11-04, 94 of 372 merged PRs waited for Alex and 74 of them (79%) were approved on the first comment: small polish went through the same gate as whole features (#3474).

  A PR that waits goes through these steps (one that does not wait does step 1, then turns on auto-merge at once):
  1. Walk the change with the run-app skill (Mac and web on a scratch app, the Remote on the walk simulator) and take **screenshots, one per state and per client**, not a video. Use only scratch data: the repo is public. The run-app skill's "Screenshots for Alex" says how, and `pr-shots.sh` puts them on the orphan branch `screenshots` (`pr-<n>/<client>-<state>.png`), so `main` gets no images.
  2. Open the PR with **auto-merge off**, the screenshots in its body under `## Screenshots`, and the label `needs-approval`. Alex's list is https://github.com/alexec/Agents/pulls?q=is%3Aopen+label%3Aneeds-approval.
  3. **Fix nothing else until Alex answers:** no CI fixes, rebases or conflict fixes, because they use tokens on a change Alex may not want. Wait with `wait_for_event` on `pr.reviewed`, `pr.commented` and `pr.closed`, `where: {"pr": <n>}` (#2838, #3860), and end the turn: a waiting lane holds no running place.
  4. **Alex answers with a review on a PR the agents' bot opened** (Approve or Request changes, on github.com or with Approve in the app's Needs you), **and with a comment on a PR posted as `alexec`** (GitHub does not let `alexec` review its own PR). `pr.reviewed` or `pr.commented` wakes the lane with the review or the comment itself (author, state, url, body), so it sets the label from that, with no need to re-read the PR. **Approve** (a review with Approve, or a comment such as "I approve these screenshots, ship it"): the lane adds `approved`. **Change it** (Request changes, or any other comment or review): the lane adds `changes-wanted`, makes the changes, takes a new set of screenshots (`pr-shots.sh` replaces the old ones), removes `changes-wanted`, says on the PR what it changed and waits again. When the lane cannot tell which one Alex means, it asks on the PR and waits again. **Drop it:** `pr.closed` wakes the lane; it cleans up and ends.
  5. After `approved`: remove `needs-approval`, write `Alex approved (<review or comment link>)` in the PR body, fix the failing checks, rebase, turn on auto-merge and land it as usual.
  - **Who an agent posts as (#3860).** Until this Mac has the agents' bot (#3858), an agent's `gh` and git post as `alexec`, so a comment an agent writes starts with `<!-- agent -->`: a comment without it is Alex's. Once the bot is installed on `alexec/Agents`, they post as `alexec-agents[bot]` (#3926): `gh pr view <n> --json author` says `app/alexec-agents`. A post as the bot needs no marker, because `pr.commented` leaves out a bot's. When a lane is not sure which it posts as, it adds the marker: it does no harm.
  - **GitHub's own rule holds the bot's PR for Alex (#3860).** `main`'s ruleset has *Require approval of changes not attributed to a person* (`require_extra_approval_for_unattributed_changes`): a PR whose changes an agent's bot made merges only after a person approves it with a review. It replaces the `agent-bots` check, removed because it did the same. A PR posted as `alexec` is not held by it: there the labels are still the only gate.
  - **A multi-PR enhancement is a stack (#1777).** It waits once, on its top PR, when any PR in it adds a screen, control or layout: Alex approves once, with screenshots of the whole feature; the stack then lands from the bottom.
  - **Voice mode** is always Alex's test, on the installed Mac app: a scratch app has no microphone or speech. Say so in the PR body.
  - The lane keeps the labels (Alex, 2026-10-27), which mirror Alex's answer: they tell the other agents and Alex's list which PRs wait and which are approved. `.github/CODEOWNERS` names no UI path (Alex, 2026-11-07, #3860): a code-owner rule there would hold every UI PR, bug fixes and polish too, where #3474 holds only a new screen, control or layout.
- **A change to an integration's state updates its row (#1283).** A PR that adds, removes, walks, tests on a real account, breaks or fixes a third-party integration updates its row in `docs/reference/integrations.md` in the same branch, as a parity line does for `parity.md`. The runtime check (Tuesday and Friday, and in each release; #3715) writes the runtime rows; edit the others by hand. An issue about an integration gets the `integration` label.
- **Alex tests every integration, later (#1782, #1838).** Alex tests each integration on a real account, of the integration and of the user experience, at a later time (Alex, 2026-10-20). An integration video (#1793) can replace that test. Agents first walk all they can on scratch set-ups. A lane does not wait for Alex's hands (a code, a CAPTCHA, a passkey) to walk a real account: it lands its code and puts the test on the checklist. The Scrum Master keeps one checklist issue for Alex (label `alex-todo`, assigned `alexec`, `## What Alex does`, no milestone), one item per integration, that says where the account is and what to check (#1781 for 0.7). Alex's test is not a milestone gate: a release does not wait for it.
- **A new App Store entitlement updates the release secrets (#2781).** A PR that adds an entitlement to an App Store target makes its profile again and updates the `release` environment's `PROFILE_…` secret in the same change (`scripts/release-secrets.sh --store`, with Alex's approval), and says so in the PR. The `testflight` job's `check-store-profiles.py` fails on a stale profile, naming the entitlement and the secret.
- **Sensitive paths have a code owner (Alex, 2026-11-10).** `.github/CODEOWNERS` names Alex as the owner of the paths where a mistake costs the most: CI and release workflows, the release and secret scripts, the deploy files, entitlements, the control plane, the control link, sign-in and the Keychain. GitHub asks Alex to review a PR that touches one, so Alex sees it; the lane lands it as usual. It replaces the `risk` check, which scored a PR's risk from its files and labelled it `risk:low`, `risk:medium` or `risk:high` (#3040): a score nobody acted on. A UI path is never in it (above).
- **Every issue gets its own agent, worktree and pull request (#2504).** No path is locked to one lane (Alex, 2026-11-10; it replaces the areas of #873): two lanes may change the same files, and the one that lands second rebases. A follow-up to a running lane's work waits until that lane's PR has auto-merge on, then a new agent starts on it; the parts of one spec, or a change and its per-client follow-ups, go one after another, each by its own agent. A running lane is never messaged to take another issue: a message to a lane is for its own PR (stuck, in conflict, failing checks), never to widen its work. A stack (#1777) is still one agent per PR. Land a change across many files (a rename, a removal) when no other lane is active.
- **An issue is taken** when a session is labelled `#<n>`, an open PR fixes it, or the session that filed it is not archived yet (it may be fixing it). Take the next one.
- **Re-arm auto-merge after a base change (#1741).** GitHub can leave a CLEAN, green PR with auto-merge on unmerged when its base moved (a stack landing, a retarget to main). After you change a PR's base, or turn auto-merge on just after its base moved, run `scripts/rearm-automerge.sh <pr>`. A lane or Scrum Master waiting on PRs to land runs `scripts/rearm-automerge.sh --stalled` each time it wakes: it re-arms, once per head, any PR that has been CLEAN with auto-merge on for 10 minutes, and says so on the PR. Wait on the `github` server's `checks.passed` event (#3035) alongside the others a lane already waits on, so this wakes as soon as a PR's checks go green rather than only at the next timer wake.
- **A stacked PR gets auto-merge only once its base is main (#1777).** A stacked PR's base is another lane branch. That base has no required checks, so `gh pr merge --auto` merges the PR into it at once (#1776, 2026-10-20). When the PR below lands, run `git rebase --onto origin/main <old base>`, set the base to main, then turn on auto-merge. If GitHub then leaves a clean PR unmerged, run `scripts/rearm-automerge.sh <pr>` (#1741).
- **Conflicting PRs land one at a time.** When more than one open PR is in conflict, one landing lane rebases and lands them in turn, and the others' auto-merge is off until it is theirs.
- **Label your session as you go** with set_session_labels: `#<n>` for the issue, `P#<n>` for the PR, and `merged` once it lands.
