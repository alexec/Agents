# AGENTS.md

## Context routing

- **For the project's purpose and setup:** READ `README.md`.
- **For architecture, terminology and decisions:** CONSULT `docs/`.
- **For a task a skill covers:** USE the skill in `.agents/skills/`.
- **When a task calls for a specialist perspective:** ADOPT a persona from `.agents/personas/`.

## Libraries before our own code

- Before writing a parser, protocol, client, format or algorithm, look for a library. Use it when one fits.
- A fit library has a permissive licence (MIT, Apache-2.0, BSD or ISC; no GPL/AGPL in the apps), was released or updated in the last 12 months, has users, and has a pinned version that Dependabot watches (`Package.resolved`, `go.sum` or an exact `package.json` version).
- Prefer the platform library (Foundation, Go standard library or the browser), then the protocol or service's official SDK, then a widely used community library.
- Write our own code only when no fit library exists or the library costs too much where it runs. State the reason in the PR. For a library added by a PR, state its purpose, licence and size.

## Durable data

- Store data in the project itself when possible.
- When important long-term data cannot safely live in the project, store it on disk in `~/.agents` when safe. Do not rely on an agent's memory for data that can safely be stored there.

## Keeping the three clients in step

- **Three clients draw the same product:** the Mac window (`App/`), the Remote on iPhone and iPad (`Remote/`), and the web page (`Web/`). `Shared/UI` is drawn by both the window and the Remote.
- **Each feature has a tier (#2796):** the Tier cell of its row in the parity table, below. The Mac window and the web page are full clients and are never trimmed; the tiers trim only the Remote.
  - **Core:** all three clients (the session list, chat, question cards, the prompt bar, approvals, notices, the Brief, and the session and folder work the Remote keeps). The parity table lists it all.
  - **Mac + web:** the Mac window and the web page. The Remote gets no parity issue and does not have the feature: #2798 removes it, with no line in its place (Alex, 2026-10-29).
  - **One client:** by design, no follow-up.
  - A new feature that is on neither of the parity table's lists is Mac + web.
- **A change to any client's UI** (`App/Sources`, `Remote/Sources`, `Shared/UI` or `Web/src`) says, in its commit, what **each of the other two** does about it, one line each:
  - the same change in this branch: `remote: same`;
  - a parity issue filed: `web: #NNN`;
  - left out on purpose: `mac: by design (no swipe on Mac)`;
  - not on the Remote because of its tier: `remote: tier mac+web`.
- **For example,** a Mac sidebar change ends with `remote: #226` and `web: same`; a new Settings ▸ People control ends with `remote: tier mac+web` and `web: same`; a web-only fix ends with `mac: same, remote: same` when both already do it. A change to docs only says `mac: docs only, remote: docs only, web: docs only`.
- **The table of where each client stands** is `specs/071-web-remote/walks/parity.md`, a file per screen under `walks/parity/` (Mac / Remote / web, a row per feature; #2020). `scripts/parity-counts.py` counts the verdicts and the tiers. A parity line that changes a row updates it in the same branch.

## Web/dist and generated.ts

- **`Web/dist` is not checked in** (#473); it is in `.gitignore`. Agents Host's build makes it with `scripts/web.sh dist` (the Node in `Web/.node-version`; without it, an empty one and a warning). Run `scripts/web.sh build`, under the "build" lease, to see a web change without a Mac build.
- **The wire's types come from `Packages/Wire` (#1135).** A change to a protocol type changes `Packages/Wire/daemon.schema.json` (or a method in its `*.openrpc.json`) first, runs `scripts/wire.sh gen`, and commits what it makes (`Web/src/protocol/generated.ts`, `Go/wire/*_gen.go`); `WireSchemaTests` then says what to change in Swift by hand. A conflict in a generated file is settled by running that again, never by hand.

## Verifying a lane's work

- **A lane verifies only what it touched:** the schemes and tests for the paths its branch changes, as `merge-wave.sh plan` lists them. An `App/` change builds `AgentsHost` and `AgentsStore`; a `Remote/` change builds the Remote; a package change runs that package's tests, filtered by `scripts/select-test-suites.sh`. The full AgentsKit suite and every scheme run once, in the merge wave, which also skips any check that already passed at the same tree.
- **Before a push that changes `Go/`, run `scripts/go-changed.sh`** under the "build" lease (#2994): `go vet` and `go test -race` on only the Go packages the branch changes (all of them for `go.mod`, `go.sum` or `Packages/Wire`). CI's runners are shared, so a Go failure found here saves a run, a macOS one too. Its container is Linux: a failure only macOS has still shows only in CI's `go-darwin`.
- **Lint with `scripts/lint.sh`** (#1224): shellcheck, `zsh -n`, our text checks, and golangci-lint's `unused` and `ineffassign` (#2162) fail CI's `lint` job. The other golangci-lint rules, govulncheck, ruff, Biome and SwiftLint only report, and say which findings are in your files (`LINT_BASE=origin/main`). On the Mac each runs in a container: nothing to install. `scripts/lint.sh --fix` runs the fix modes.
- **Build through `scripts/build-cache.sh`** (`… xcodebuild …`, `… swift test …`): one package and compilation cache in `~/Library/Caches/Agents-build/` for every worktree, so a fresh worktree is not a cold build. Deleting a worktree's own `build/` and `.build` when done is still the rule; the cache stays. Its `swift test` sets `AGENTS_QUARANTINE=1`, so tests marked `.flakyUnderLoad` skip as on CI; `AGENTS_QUARANTINE=0` runs them.
- **Before any xcodebuild, swift build, swift test, scripts/web.sh build or ship.sh, lease the resource "build" with lease_resource (minutes sized to the job, at most 60), and release it with release_resource the moment the command ends.** Never hold it while reading, editing or waiting on the screen.
- **Close every scratch app you ran** (run-app, the walk simulator, headless Chrome) with the run-app skill's "When you are done" steps before you commit or end. A scratch app left running is a bug in the lane.
- **A walk does not hold a place:** a lane that needs one commits, hands the walk on, and ends.

## Work by milestone (#1340)

- **Work goes by milestone.** The Scrum Master takes issues from the earliest open milestone first, bugs before features. An issue with no milestone is the backlog, except `polish` and `competitor` issues, which have standing lanes of their own.
- **A filed issue gets a milestone** only when it serves that milestone's goal (#1340). Bugs are the exception: they always go in the open milestone.
- **Bugs go in the open milestone.** A bug is filed into the open milestone, whatever its theme. When a release ships, the release skill moves the milestone's open bugs before it closes the milestone: after a minor (x.y.0), to its patch milestone x.y.1; after a patch, to the next minor milestone.
- **Polish and competitor gaps have no milestone.** Issues labelled `polish` or `competitor` stay out of milestones. The exception is a competitor gap that serves a milestone's goal; it keeps that milestone. At least one standing lane works them alongside the milestone lanes, highest RICE first, under the same area and open-PR limits. They are for no milestone, so they can merge before a release ships (#1570), except while a patch milestone is open (below).
- **Only the open milestone is workable (Alex, 2026-10-22, #2309).** The next one starts when the open one ships; until then its issues, and every later milestone's, keep `parked`. The release takes `parked` off when their milestone becomes the open one.
- **Spare places go in this order** (#1604, #2309), always within the area and open-PR limits: the open milestone's work and bugs; then `polish` and `competitor` issues (the standing lane, #1570), by RICE; then backlog issues with no milestone, bugs first, then by RICE. No place ever goes to the next milestone's work.
- **UI changes go early (Alex, 2026-10-22, #2337).** Every choice of what to work on next goes in this order: `priority:high` issues first; then **UI changes**, anything that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`), in the open milestone and in the backlog alike, bugs before features; then the rest, in the order above (the open milestone, then `polish` and `competitor`, then backlog bugs, then the backlog by RICE). A UI lane gets a place before a non-UI lane. When places run short, pause a non-UI lane, never a UI one. **Why:** a person must review each UI change, so it must get to `main` and TestFlight early. A UI enhancement gets its place early too, but merges only after Alex approves it ("A UI enhancement waits for Alex", below, #2811).
- **Core usability goes first (Alex, 2026-10-27, #2800).** When milestones are put in order, a milestone that improves the app's core usability goes before the others. Core usability is what a person does in the app every day: start a session, choose a runtime, read and answer agents. A milestone that is useful to one person is core usability; a milestone that reaches people who are not the user (Hosted, Channels) is not. **Why:** this is why 0.13 Auto runtime and voice mode and 0.14 Lineage and value go before 0.15 Hosted and 0.16 Channels. The order is in #1340 and in each milestone's description.
- **A minor release is followed by a patch (Alex, 2026-10-27, #2801).** When x.y.0 ships, the release makes the milestone `x.y.1 Bug fixes` and moves the open bugs into it. The patch milestone is the open milestone until it ships; the next minor milestone keeps `parked`. **Why:** many bugs come up in a .0 version, and a patch gets their fixes to people sooner than the next minor's features would.
  - **A patch only fixes bugs.** While a patch milestone is open, only bug fixes merge to `main`. A `polish`, `competitor` or backlog enhancement PR gets `hold:v<x.y.z>` (auto-merge off) and waits for the patch to ship; lanes still work on it, and only the merge waits. The `hold` check fails while the label is on, and turns auto-merge off when someone turns it on (#2931); `scripts/rearm-automerge.sh` never arms a held PR. Only the release takes the label off.
  - **A patch runs no reviews or checks** (no security, performance, HADR, dead-code, runtime, usability or competitor run, no feature-matrix update): those run once per minor. It still has the gate, the notes, the tag, the GitHub release, both TestFlight builds, the control plane deploy and closing the milestone, and it is still at most one release a day.
  - **A patch is ready** when no `priority:high` or `priority:medium` bug is open in it, or two days after the last tag, whichever comes first. A low bug does not hold a patch. Alex still starts the release.
  - **One patch by default.** After x.y.1 ships, its open bugs go to the next minor milestone, which becomes the open one. The release makes x.y.2 only when a `priority:high` bug is still open.
- **A patch milestone holds only patches (#2779).** A milestone planned as a patch (x.y.z) holds no enhancement and removes no capability, or it ships as a minor. Only an enhancement that changes a client's UI, the host or daemon, or the capability list counts; a tooling, workflow or docs enhancement does not (#2857). When `release-plan.py`'s version differs from the open milestone's, the release asks Alex which to use.
- **A milestone never closes with open issues (Alex, 2026-10-22, #2455).** Before the release skill closes it, its open bugs move to the next open milestone (the patch milestone after a minor) and every other open issue moves to the backlog. **Why:** nothing schedules an issue left in a closed milestone.
- **One release a day (Alex, 2026-10-22, #2462).** At most one tag per calendar day in America/Los_Angeles; the release skill's readiness check and gate wait for the next day. A patch release counts too. The day after a release, lanes work bugs first; while a patch milestone is open, they work its bugs first.
- **A milestone is done when its release has shipped** (the GitHub release and both TestFlight builds), not when GitHub closes it. No change for the next milestone merges to `main` before that (Alex, 2026-10-18). The release skill closes the milestone.

## Landing a change

- **Every change has an issue and a pull request.** Work on a branch of your own, in a worktree you moved into with move_worktree (never one made by hand with `git worktree add`, which the app never sees: #615), push it, open the PR with `gh pr create`, turn on `gh pr merge --auto --squash` at once, and wait for it to land; fix what CI fails. Never push to `main`.
- **A UI enhancement waits for Alex (Alex, 2026-10-27, #2811).** An `enhancement` PR that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`) merges only after Alex approves it. A bug fix, and an enhancement that changes no client (daemon, tooling, docs), merge with auto-merge at once as before. **Why:** agents' walks find out whether a change works, not whether it is right for a person; 102 of the 296 bugs filed from 2026-10-20 to 10-27 came from the usability check, after the change had merged.
  1. Walk the change with the run-app skill (Mac and web on a scratch app, the Remote on the walk simulator) and take **screenshots, one per state and per client**, not a video. Use only scratch data: the repo is public. The run-app skill's "Screenshots for Alex" says how, and `pr-shots.sh` puts them on the orphan branch `screenshots` (`pr-<n>/<client>-<state>.png`), so `main` gets no images.
  2. Open the PR with **auto-merge off**, the screenshots in its body under `## Screenshots`, and the label `needs-approval`. Alex's list is https://github.com/alexec/Agents/pulls?q=is%3Aopen+label%3Aneeds-approval.
  3. **Fix nothing else until Alex answers:** no CI fixes, rebases or conflict fixes, because they use tokens on a change Alex may not want. Wait, and end the turn: a waiting lane holds no running place. It still holds its `area:` (#873).
  4. **Alex answers with a comment on the PR** (GitHub does not let `alexec` approve or request changes on its own PR). The lane reads it and sets the label. **Approve** (for example "I approve these screenshots, ship it"): the lane adds `approved`. **Change it** (any other comment): the lane adds `changes-wanted`, makes the changes, takes a new set of screenshots (`pr-shots.sh` replaces the old ones), removes `changes-wanted`, says on the PR what it changed and waits again. When the lane cannot tell which one Alex means, it asks on the PR and waits again. **Drop it:** Alex closes the PR; the lane cleans up and ends.
  5. After `approved`: remove `needs-approval`, write `Alex approved (<comment link>)` in the PR body, fix the failing checks, rebase, turn on auto-merge and land it as usual.
  - Every PR and comment is posted as `alexec`, so start each comment an agent writes on a PR with `<!-- agent -->`: a comment without it is Alex's.
  - **A multi-PR enhancement is a stack (#1777).** Alex approves once, on the top PR, with screenshots of the whole feature; the stack then lands from the bottom.
  - **Voice mode** is always Alex's test, on the installed Mac app: a scratch app has no microphone or speech. Say so in the PR body.
  - Alex approves with a comment, and the lane keeps the labels (Alex, 2026-10-27): the labels tell the other agents and Alex's list which PRs wait and which are approved. A machine account for the agents, with CODEOWNERS to make Alex's review required, is the later option. Until #2838 adds an event for a person's comment on a PR, a waiting lane wakes on a timer and reads the comments; #2839 reports a UI enhancement that merges without `approved`.
- **A change to an integration's state updates its row (#1283).** A PR that adds, removes, walks, tests on a real account, breaks or fixes a third-party integration updates its row in `docs/reference/integrations.md` in the same branch, as a parity line does for `parity.md`. The weekly runtime check writes the runtime rows; edit the others by hand. An issue about an integration gets the `integration` label.
- **Alex tests every integration, later (#1782, #1838).** Alex tests each integration on a real account, of the integration and of the user experience, at a later time (Alex, 2026-10-20). An integration video (#1793) can replace that test. Agents first walk all they can on scratch set-ups. A lane does not wait for Alex's hands (a code, a CAPTCHA, a passkey) to walk a real account: it lands its code and puts the test on the checklist. The Scrum Master keeps one checklist issue for Alex (label `alex-todo`, assigned `alexec`, `## What Alex does`, no milestone), one item per integration, that says where the account is and what to check (#1781 for 0.7). Alex's test is not a milestone gate: a release does not wait for it.
- **A new App Store entitlement updates the release secrets (#2781).** A PR that adds an entitlement to an App Store target makes its profile again and updates the `release` environment's `PROFILE_…` secret in the same change (`scripts/release-secrets.sh --store`, with Alex's approval), and says so in the PR. The `testflight` job's `check-store-profiles.py` fails on a stale profile, naming the entitlement and the secret.
- **One lane per feature area at a time (#873).** `.agents/areas` maps paths to areas (`sidebar`, `events`, `agent-tools`, `brief`, `workspaces`); the `areas` CI step labels each PR `area:<name>` from its files and warns when another open PR holds the same area. An issue you file gets its `area:<name>` label when it has one. Do not start an issue whose area an open PR or a running lane holds: take the next one. **Every issue gets its own agent, worktree and pull request (#2504).** A follow-up in an area a running lane holds waits until that lane's PR has auto-merge on, then a new agent starts on it; the parts of one spec, or a change and its per-client follow-ups, go one after another, each by its own agent. A running lane is never messaged to take another issue: a message to a lane is for its own PR (stuck, in conflict, failing checks), never to widen its work. A stack (#1777) is still one agent per PR. Land a change across many files (a rename, a removal) when no other lane is active. `scripts/replay-conflicts.py` counts the conflicts PRs met.
- **An issue is taken** when a session is labelled `#<n>`, an open PR fixes it, or the session that filed it is not archived yet (it may be fixing it). Take the next one.
- **Re-arm auto-merge after a base change (#1741).** GitHub can leave a CLEAN, green PR with auto-merge on unmerged when its base moved (a stack landing, a retarget to main). After you change a PR's base, or turn auto-merge on just after its base moved, run `scripts/rearm-automerge.sh <pr>`. A lane or Scrum Master waiting on PRs to land runs `scripts/rearm-automerge.sh --stalled` each time it wakes: it re-arms, once per head, any PR that has been CLEAN with auto-merge on for 10 minutes, and says so on the PR.
- **A stacked PR gets auto-merge only once its base is main (#1777).** A stacked PR's base is another lane branch. That base has no required checks, so `gh pr merge --auto` merges the PR into it at once (#1776, 2026-10-20). When the PR below lands, run `git rebase --onto origin/main <old base>`, set the base to main, then turn on auto-merge. If GitHub then leaves a clean PR unmerged, run `scripts/rearm-automerge.sh <pr>` (#1741).
- **Conflicting PRs land one at a time.** When more than one open PR is in conflict, one landing lane rebases and lands them in turn, and the others' auto-merge is off until it is theirs.
- **Label your session as you go** with set_session_labels: `#<n>` for the issue, `P#<n>` for the PR, and `merged` once it lands.
