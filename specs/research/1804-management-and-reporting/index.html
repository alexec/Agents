Management and reporting in the control plane

Concepts · 2026-10-20 · #1804 · Team (#994–#997) and Enterprise (#998–#1002) tiers · nothing here is built

When a team or a company uses Agents, two new needs come up. Admins must manage the system: people, machines, policy, keys and catalogues. Everyone wants reports: what the agents cost, what they did and where the time went, above the level of one person. This page puts both inside the control plane, as two sub-apps of the one Go binary. There is no second deployment.

1 · The shape2 · The scope ladder3 · Console concepts 4 · Reports concepts5 · How the data gets there6 · Slices and roadmap7 · Decisions

1 · The shape: one binary, four sub-apps

The control plane already holds a router and serves the web client. Add two sub-apps beside them. All four use the same sign-in, the same roles and the same store. One web bundle (Web/) gets two new top-level routes, /console and /reports. A switcher at the top moves between them, like Google Workspace or GitHub's org settings.

Rule that makes this safe: the control plane gets numbers and events, never conversation text. This keeps the promise in docs/explanation/control-plane.md: conversations stay on the host. A report links back to the session; the session opens on its own machine, and only for a person who may see it.

2 · The scope ladder: one report, three zoom levels

Do not make a second set of reports for teams. Each report has one design and a scope. Your role sets the highest scope you can see. The Mac and the Remote already draw the "Me" level (Cost, Time, Pool). The control plane adds the two levels above.

3 · Console concepts (management)

Nine concepts. Three are drawn as screens below the list. Each card says which roadmap issue it serves.

M1 · Fleet board

Every machine, at a glance

A table of machines: who owns it, online or not, agentsd version, running agents, disk, runtimes signed in, last seen.

  • Drain: stop new work, let turns end
  • Push an update to old versions
  • Filter: offline, out of date, disk low

M2 · People and groups

Directory and joins

People, bots, groups and roles. An approve-to-join queue for new machines and new people. SCIM later fills it from the company directory.

  • Remove a person: stop and delete their started machines
  • Bots: owned by a group, run team workflows
T1 #994T9 #1002#1761
M3 · Policy studio

Rules in layers, with a preview

Org → group → person → project. Each rule can be set or locked at a level. "View as" shows the effective policy for one person and project, and why.

  • Runtimes and models allowed
  • Sandbox floor, MCP allow list
  • Spend caps, worktree rules

M4 · Keys and gateways

Org keys, not personal keys

Model keys and gateways (Bedrock, Vertex, Azure, base URL) held by the control plane, sealed with KMS. Assign per group. Rotate on a date. See which machines still use an old key.

M5 · Catalogue governance

Approved MCP servers and skills

One list of approved MCP servers, skills and marketplaces. A person can request one; an admin approves it once for a group. Shows who uses each and its last version.

M6 · Team workflows and bots

Shared automation

Workflows run by a group's bot, with runs-on: labels. See the queue, runs and failures per bot. Pause one for everyone.

M7 · Requests inbox

One place for "may I?"

Join requests, a raise of a spend cap, a new MCP server, a new runtime. Approve or refuse in one click, from web, email or a chat MCP. Same idea as Needs You, but for admins.

M8 · Audit trail

Who did what

Every host action with its actor: started, stopped, approved, changed policy, read a secret. Filter, then export or stream to an audit sink (S3, Splunk, OTLP).

M9 · Live operations

The control tower

All agents running now, across the org: who, which machine, how long, cost so far, waiting on whom. Stop one, stop all on a machine, or stop all with a runaway cost. A "big red button" for an incident.

4 · Reports concepts

Eight concepts. Every one uses the scope ladder. Four are drawn below. The data in the drawings is made up.

R1 · Spend and budget

Where the money goes

Cost by group, person, project, runtime and gateway. Budget line and a forecast to month end. A chargeback CSV per cost centre.

#823 usage history#829 by label
R2 · Outcomes

What the agents shipped

Sessions → PRs (or MRs) opened → merged → reverted. Cost per merged PR. Cycle time from first prompt to merge. Uses the GitHub and GitLab events we already get.

events server github#1631 GitLab
R3 · Where the time goes

Is the person the bottleneck?

Agent working, tools, waiting on a person, queued. The median time a question waits for an answer, per person and per hour of day. Grows the Time page (#852) to the team.

#852 Time page
R4 · Runtime scorecard

Which runtime earns its cost?

Per runtime and model: cost per merged PR, error rate, compactions, availability, allowance left. Helps choose defaults in Policy.

#47 assess-runtimePool page
R5 · Adoption

Who uses it, and how

Weekly active people, sessions per person, workflows in use, runtimes in use, new joins. A seat report for licence and "is the rollout working?".

R6 · Workflow health

Is the automation healthy?

Runs, failures, queue depth, run time, cost per run, per workflow and per bot. The "red" list first.

#422 queue#1761 bots
R7 · Compliance pack

For the auditor

Policy blocks, secret reads, sandbox escapes refused, data erasures, key rotations. A signed PDF or ZIP per quarter, from the audit trail.

5 · How the data gets there

Reports must be fast at org scale and must not grow without a bound (bound data, not concurrency). So each machine rolls up its own numbers. The control plane only adds roll-ups together. All stores are plain files, as today.

7 · Decisions (Alex, 2026-10-20, #1804)

1. The Console is its own app in the switcher, not a part of Settings.
Settings is per person and per machine. The Console is the organisation.
2. A group lead sees spend and time per person, with a policy switch for "totals only".
Some works councils require totals only. R3 talks about agents, not people.
3. R2 Outcomes counts PRs and MRs first.
They are the events we already get from GitHub and GitLab.
4. Outside tools: CSV first, then OTLP metrics, then a read API when someone asks for it.
